# 일반 LH2 방출 종료 근거 감사와 남은 작업

## 현재 계산 연결

현재 일반 LH2 진단 캠페인은 24개 사건을 생성한다. 24개 사건 모두에서

`설비 상태 → provider 방출 packet → 지속시간·방출질량 → SLABx-LH2 → 점화·기상 → 피해량 → IR/F-N`

의 계산 연결이 확인되었다. 이 결과는 계산 경로가 끊기지 않았다는 뜻이다. 현장 설비의 방출 종료시간이나 격리 성능을 실제 자료로 확인했다는 뜻은 아니다.

## 자동 집계 결과

`results/20261106/generic_lh2_provider_release_closure_current.json`은 24개 사건과 26개 provider packet을 검사한다.

| 항목 | 결과 |
|---|---:|
| 전체 사건 | 24 |
| provider packet 경로 | 24 |
| 내부 provider packet | 26 |
| 종료 근거가 준비된 사건 | 9 |
| 종료 근거가 열린 사건 | 15 |
| qualification으로 승격된 packet | 0 |
| 시설 QRA 승격 | 불허 |

열린 원인은 두 종류다.

- 15개 사건은 `synthetic_diagnostic_horizon`처럼 고정 진단시간 또는 압력 평형을 종료조건으로 사용한다. 실제 차단·격리 기록이 필요하다.
- 현재 `inventory_depletion` 사건에서 provider 질량수지 부족으로 열린 사건은 없다. 다만 이 결과는 provider 원장이 실제 설비의 reviewed inventory라는 뜻은 아니다.
- 5개 저장탱크 사건은 provider 검증 sidecar의 양수 재고 임계값·잔류질량·질량잔차를 packet digest와 대조해 종료근거를 닫았다. 이 검사는 zero-mass 소진을 주장하지 않으며, provider qualification과 독립 물리검증은 여전히 열려 있다.
- vaporizer G1은 provider response의 `cumulative releasable mass until atmospheric-pressure equilibrium` 원장과 잔류질량을 packet digest에 결합해, 대기압 평형까지 방출 가능한 재고가 소진된 경우로 닫았다. upstream 설비 전체 재고가 0이 되었다고 해석하지 않는다.

DynamicHEMPipe exporter에는 이제 `--inlet-isolation-time-s`와 `--termination-threshold-kg` 선택 입력이 있다. 격리 후 provider 상태를 계속 적분하고 양수 임계값에 도달하면 종료하며, 100개를 넘는 내부 시간간격은 질량·정적 엔탈피 적분을 보존하는 방식으로 압축한다. 이 기능은 현재 generic 24개 catalog에 임의로 적용하지 않았다. 15개 열린 사건에는 설비별 검토된 격리시각과 임계값이 먼저 필요하다.

나머지 9개는 현재 감사 규칙상 종료 경계가 준비된 사건이다. 이 중에서도 qualification은 별도의 공급자 검토와 독립 물리검증이 필요하므로 자동으로 승격하지 않는다.

## “얼마나 더”의 의미

코드 연결 자체는 이번 범위에서 마무리 단계다. 남은 개발은 15개 열린 사건의 증거를 채우고, 그 자료로 재실행하는 일이다.

1. transfer-line, transfer-valve, transfer-pump, vaporizer와 일부 storage 사건에 실제 차단·격리시간을 연결한다.
2. inventory-depletion 사건은 provider가 초기질량·최종질량·질량수지 잔차를 출력하도록 한다.
3. 같은 packet으로 SLABx-LH2 결과를 다시 만들고 질량잔차와 종료시각을 재검사한다.
4. 실제 일반 시설의 reviewed port, 기상·점화·인구 입력을 확인한다.
5. 독립 holdout 자료로 누출·액적·풀·확산 결과를 검증하고, 처리시간을 fresh physics와 cache로 각각 측정한다.

각 열린 packet에는 이제 `prism.provider_release_closure_request.v1` 요청 블록이 함께 기록된다. 요청 블록은 현재 packet의 event/component/port, 종료근거와 질량값, blocking reason을 보존하면서, 장비 종류에 맞는 차단시각·재고장부·provider history 항목을 요구한다. 이 블록은 자료 수집을 구체화할 뿐이며, 입력값을 추정하거나 packet을 qualified로 바꾸지 않는다.

열린 요청만 별도로 내보내려면 다음 명령을 사용한다.

```powershell
python scripts/export_generic_provider_closure_requests.py `
  --packet-evidence results/20261031/native_generic_scope_packets_pipefix/packet_evidence.json `
  --packet-root results/20261031/native_generic_scope_packets_pipefix `
  --output results/20261106/generic_lh2_provider_closure_requests.json
```

현재 산출물은 15개 요청을 포함하며, 각 요청은 `prism.provider_release_closure_request.v1`이다.

### qualification sidecar exact-match 감사

catalog에 기록된 요청을 실제 폴더의 `provider_qualification.json`,
`provider_qualification_evidence.json`, `qualification_sidecar.json` 또는
`qualification.json`과 대조하는 별도 감사기를 추가했다. 감사기는 각 요청에서
`event_id`, `component_id`, `port_id`, `provider_source_digest`,
`provider_result_digest`를 하나씩 정확히 비교한다. 자료가 없거나 해시·설비 식별자가
다르면 qualified로 세지 않는다.

현재 [`results/20261106/generic_lh2_provider_evidence_audit_current.json`](../results/20261106/generic_lh2_provider_evidence_audit_current.json)은
26개 요청을 검사해 sidecar 존재 0개, exact match 0개, qualified provider packet 0개로
기록한다. 이 감사 결과는 readiness와 IJHE 목표 감사에 연결되어 있지만, sidecar가
정확히 맞더라도 독립 물리검증·빈도·시설 QRA를 자동으로 열지 않는다.

양단 방출 packet은 하나의 sidecar 안에 포트 배열과 source/result digest 배열을
packet 순서대로 기록하면 양쪽을 함께 exact-match한다. 공급자 자료가 별도 폴더에
보관되는 경우 catalog 요청의 `qualification_sidecar_path`로 명시 경로를 전달할 수
있다. 감사기는 경로를 추정해 다른 파일을 끌어오지 않는다.

```powershell
python scripts/audit_generic_provider_evidence.py `
  --catalogue results/20261106/generic_lh2_provider_evidence_requests.json `
  --output results/20261106/generic_lh2_provider_evidence_audit_current.json
```

공급자 sidecar를 별도 검토 폴더에 보관할 때는 catalog를 수정하지 않고 manifest를
추가한다.

```powershell
python scripts/audit_generic_provider_evidence.py `
  --catalogue results/20261106/generic_lh2_provider_evidence_requests.json `
  --sidecar-manifest path/to/provider_qualification_manifest.json `
  --output results/20261106/generic_lh2_provider_evidence_audit_current.json
```

manifest 형식은 `prism.provider_qualification_sidecar_manifest.v1`이며, 각 항목은
`request_id`와 `qualification_sidecar_path`를 가져야 한다. 양단 release set은 두
request ID를 같은 sidecar 파일에 연결한다.

제출 폴더를 처음 준비할 때는 catalog에서 빈 manifest 양식을 자동으로 만들 수 있다.
현재 26개 요청에 대해 packet의 event/component/port와 source/result digest를 미리
채우고, 같은 ordered release set의 요청에는 같은 sidecar 경로를 넣는다.

```powershell
python scripts/build_provider_sidecar_manifest_template.py `
  --catalogue results/20261106/generic_lh2_provider_evidence_requests.json `
  --output results/20261106/generic_lh2_provider_qualification_sidecar_manifest_template.json
```

생성되는 [`generic_lh2_provider_qualification_sidecar_manifest_template.json`](../results/20261106/generic_lh2_provider_qualification_sidecar_manifest_template.json)은
`TEMPLATE_ONLY` 상태다. `REPLACE_WITH_REVIEWED_SIDECARS/...` 경로를 실제 검토된
`prism.provider_qualification_evidence.v1` 파일로 바꾸기 전에는 증거로 인정되지 않고,
빈도·시설 QRA·qualification을 열지 않는다. 이 양식은 누락된 자료를 빠르게 확인하기
위한 작업 목록이지, 빈 sidecar를 제출하는 방법이 아니다.

### 설비·사고군·case 경계 감사

종료 worklist가 어떤 설비와 사고 family를 실제로 가리키는지도 별도 장부로
대조했다. [`equipment_family_case_bridge_audit.json`](../results/20261106/equipment_family_case_bridge_audit.json)은
일반 설비 7개, 사고 family 12개, case 44개를 `asset_id`와
`scenario_families`로만 결합한다. 첫 대조에서는 9개 case asset 중 2개가 현재
일반 설비 표에 없었고, 이후 provider packet의 component ID와 선언된 사고군만
후보 identity manifest로 연결했다.

- `inventory-depletion-pipe`: 10개 case
- `vertical-handoff-vent`: 10개 case

현재 원장의 상태는 44개 case 중 24개가 선언된 설비·사고 family에 직접
결합되고, 20개가 `inventory-depletion-pipe`와 `vertical-handoff-vent`의
`CANDIDATE_IDENTITY_ONLY`로 남아 있다. 이는 계산 결과가 없다는 뜻이 아니라,
P&ID identity와 사고 port가 검토되지 않았다는 뜻이다. 전체
case의 종료·격리·provider qualification 문턱은 여전히 열려 있다. 현재
gap 집계는 `ISOLATION_OPEN=44`, `PROVIDER_QUALIFICATION_OPEN=44`,
`TERMINATION_OPEN=24`, `INVENTORY_CLOSURE_OPEN=15`이다.

이 장부는 후보 두 asset을 기존 설비로 억지로 합치지 않는다. 해당 asset의
P&ID identity, 사고 port, 설비 종류를 독립 검토한 뒤에만 crosswalk에
`resolved`로 추가해야 한다. 현재 후보 manifest는 다음 파일이다.
`examples/generic_case_asset_candidate_manifest.json`.
재현 명령은 다음과 같다.

```powershell
python scripts/audit_equipment_family_case_bridge.py `
  --equipment-scenario-coverage results/20261105/generic_lh2_full_scope_equipment_scenario_coverage.json `
  --release-closure-worklist results/20261106/release_closure_worklist.json `
  --candidate-manifest examples/generic_case_asset_candidate_manifest.json `
  --output results/20261106/equipment_family_case_bridge_audit.json
```

이 결과는 최신 readiness 원장의 `chain.equipment_family_case_bridge`에도
연결되어 있다. `facility_qra_claim`, 빈도 추론과 물리검증은 계속 false다.

## 외부 설비 산출물 재검토 결과

외부 디지털트윈 폴더의 `tmp_native_contract`도 다시 확인했다. `provider_response.json` 7개가 발견되었지만, 모두 `NATIVE_EXTERNAL_ACCIDENT_EXPORT_EXECUTED_DIAGNOSTIC`이고 `input_origin=model_prediction`이다. `pipe`의 `reviewed_isolation_success`와 `layered`의 `inventory_depletion`도 모델 진단 종료조건일 뿐, 실제 설비의 검토된 운전기록이나 독립 검증을 뜻하지 않는다.

현재 generic 24개 사건과 `event_id`, `component_id`, `port_id`, `provider_source_digest`, `provider_result_digest`를 모두 대조한 결과 정확히 일치하는 packet은 0개였다. 별도의 `prism.provider_qualification_evidence.v1`, 독립 물리검증, 시설 QRA 주장도 0개다. 따라서 이 파일들을 현재 15개 열린 요청에 임의로 연결하거나 빈도를 만들지 않았다.

전체 디지털트윈 모델 루트의 release·validation 산출물도 별도로 읽기 전용 검토했다. 관측 release packet은 `metadata_confirmed_count=0`, `release_ready_count=0`이고, 공식 독립검증은 raw historian/DCS/PLC 세션 0개, 공개 가능한 시나리오 0개, 공식 점수 `null`이었다. parameter release packet은 필수 44개 중 39개가 미확인이고 center 승격 0건이며, topology linkage는 구조적으로 8개 시나리오를 설명하지만 수치 조립에 준비된 edge는 0/27이다. 따라서 이 폴더의 모델은 topology·구성품 계약·스크리닝 진단에는 유용하지만, 현재 generic 사고 packet이나 빈도·시설 QRA 증거로 자동 승격할 수 없다. 상세 해시와 판정은 [`results/20261106/external_lh2_model_root_review.json`](../results/20261106/external_lh2_model_root_review.json)에 보존했다.

이 검토는 다음 명령으로 재현할 수 있다. `--closure-audit`를 주면 외부
`provider_response.json`과 현재 generic packet의 event/component/port/source/result
digest를 함께 비교한다.

```powershell

  --source-root "C:\Users\lyul\Desktop\DocuData\액화수소 저장탱크_밴트 시스템\06_액화수소_디지털트윈_물리모델" `

```

재현 결과는 [`results/20261106/external_provider_artifact_match_review.json`](../results/20261106/external_provider_artifact_match_review.json)에 기록했다. 다음 명령으로 같은 검사를 다시 실행할 수 있다.

같은 규칙으로 다시 대조했다. 중심 native contract 7개 후보, 이전 PRISM IJHE
step-1 산출물 2개 후보, 검사센터 원본 0개 후보가 발견됐지만, 전체 9개 후보 중
현재 generic event/component/port/source/result digest와 exact-match한 것은 0개이고
qualification sidecar도 0개였다. 결과는
[`results/20261106/external_provider_roots_match_review.json`](../results/20261106/external_provider_roots_match_review.json)에
보존했다. 따라서 외부 파일을 현재 사고빈도나 시설 QRA에 재사용하지 않았다.

sidecar가 나중에 exact-match되면 readiness 원장은 그 개수를 진전으로 받아들이되,
빈도나 시설 QRA를 자동으로 열지는 않는다. 시설 case ledger가 같은 packet을 실제로
소비하고 독립 물리검증·전체 설비범위가 닫혀야 다음 승격 단계로 넘어간다.

## 남은 작업량과 예상 소요

로컬 전체 검증은 921개 테스트 통과, 1개 건너뜀이다. 재현 가능한 Python 3.12
단일 CI workflow를 `.github/workflows/ci.yml`에 추가했지만, 현재 셸에서는
비공개 GitHub 저장소의 최신 Actions 실행 로그를 인증 없이 읽을 수 없으므로
원격 실행 성공은 단정하지 않는다. 조건부 계산 연결 자체는 완료됐고, 남은
작업은 코드보다 외부 증거에 좌우된다.

| 구간 | 남은 일 | 예상 소요 |
|---|---|---:|
| 코드·재실행 | 검토된 provider packet을 catalog 26개 요청에 digest로 연결하고, 종료·질량수지·SLABx-LH2·IR/F-N을 재실행 | 자료가 준비된 뒤 1–2일 |
| 시설 범위 | receiving boundary와 현재 6개 partial 설비의 사고 경계를 확정하고, 44개 case의 격리·종료시각을 닫음 | 자료가 준비된 뒤 1–2일 |
| 물리검증 | raw historian 또는 독립 실험의 단위·시간축·센서/실험 조건·결과 파일을 확인하고 hold-out 비교 | 자료 상태에 따라 2–5일 |
| 논문용 마무리 | 불확실성·처리시간·미계산 범위 표와 재현 명령을 고정하고 Actions 재검증 | 0.5–1일 |

따라서 검토된 외부 자료가 바로 제공되면 **대략 3–5 작업일**의 코드·재실행 작업이 남아 있다. raw historian과 독립 검증자료가 아직 없으면 이 기간으로 논문 수준의 strict 승격 완료일을 약속할 수 없다. 그 경우 PRISM은 현재처럼 조건부 진단 버전으로 유지되고, 필요한 자료가 들어오는 순간 같은 감사 명령으로 남은 case 수를 다시 계산한다. 현 시점에서 반드시 필요한 외부 자료는 `44개 case` 전부가 아니어도 되지만, 최소한 선언할 시설 범위의 각 설비에 대해 exact identity가 맞는 provider packet, 격리·재고 종료 원장, 그리고 독립 검증 입력이 있어야 한다.
