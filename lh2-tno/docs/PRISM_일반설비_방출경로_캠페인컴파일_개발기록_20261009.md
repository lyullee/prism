# PRISM 일반 설비 방출경로 캠페인 컴파일 기록

2026-10-09. 일반 설비 매니페스트, 문헌 `FrequencyPlan`, 방출 요청 템플릿과 연간 기상·인구 조건을 하나의 `RiskCampaign`으로 컴파일하는 경로를 추가했다.

## 연결 방식

`src/lh2_tno/campaign_template.py`의 컴파일러는 먼저 매니페스트가 `EXECUTABLE`인지 확인한다. 이어서 `generate_events()`가 만든 모든 문헌 LOC를 순회한다.

- 설비 ID와 방출 개구가 요청 템플릿과 일치하면 요청을 캠페인 템플릿으로 보존한다.
- 캠페인 실행 시에만 해당 사건의 빈도와 현재 기상 조건을 바인딩한다.
- 개구가 다르거나 설비가 다르면 크기를 바꾸거나 다른 설비 요청을 재사용하지 않고 `UNCOMPUTED` 사유를 만든다.
- 컴파일 단계는 물리 backend를 실행하지 않는다.

실행 명령은 다음과 같다.

```powershell
.venv\Scripts\python.exe lh2-tno/scripts/build_equipment_campaign.py `
  --manifest lh2-tno/examples/equipment_manifest.json `
  --frequency-plan lh2-tno/examples/equipment_frequency_plan.json `
  --request-template lh2-tno/examples/equipment_consequence_template.json `
  --annual-conditions lh2-tno/examples/equipment_annual_conditions.json `
  --scope-provenance "synthetic generic manifest campaign" `
  --output equipment_campaign.json
```

## 합성 예제 결과

예제 FrequencyPlan은 저장탱크 5개 area-bin과 이송배관 5개 area-bin을 생성한다. 요청 템플릿의 개구는 저장탱크 `AREA_0.01%`와만 일치하므로 컴파일 결과는 **10개 사건, 요청 연결 1개, 미계산 9개**다.

이 캠페인을 현재 pinned backend로 실행한 진단에서는 저장탱크 사건 1건이 방출→확산→점화→피해→수용점 IR/F-N까지 실행되었고, 9건은 `UNCOMPUTED`로 남았다. 실행된 사건의 새 물리 계산 시간은 약 3.77초, 전체 캠페인은 약 4.14초였다. known contribution IR은 합성 수용점에서만 기록했고, 전체 시설 IR/F-N은 `null`로 유지했다.

## 해석 한계

예제의 탱크 상태·방출 지속시간·점화확률·인구·기상은 합성값이다. 컴파일러가 `EXECUTABLE` 캠페인을 만들었다는 사실은 실제 설비의 provider 방출 이력이나 현장 신뢰도를 증명하지 않는다. 검사센터 자료는 아직 `PARTIAL`이므로 이 경로에 실제 센터 결과를 넣어 시설 위험으로 승격하지 않았다.

다음 승격 조건은 실제 설비별 provider 방출·차단·재고 소진 이력, 실제 포트와 수용점, 검토된 점화·인구·기상 조건을 동일한 계약으로 제공하는 것이다. 하나라도 빠지면 현재처럼 사건별 미계산과 known contribution을 분리한다.

## 복수 설비 방출 요청 catalog

실제 옥외 시설은 탱크, 이송배관, 밸브 또는 다른 설비마다 서로 다른 provider 방출 경계를 가질 수 있다. `build_equipment_campaign_from_catalog()`와 CLI의 `--request-catalog`은 여러 `ConsequenceRequest`를 한 번에 받아 빈도 사건별로 선택한다. 선택 조건은 요청의 `component_id`와 provider가 선언한 실제 failure opening이다. 개구가 다른 요청을 크기만 바꾸어 재사용하지 않으며, 같은 사건에 두 요청이 맞으면 모호성 오류를 낸다.

이 기능은 설비별 결합을 위한 컴파일 단계다. 실제 설비 모델이 방출 이력·위치·상·지속시간·종료 장부를 제공하지 않는 상태에서 물리 계산을 대신하지 않는다. 요청 catalog에 없는 사건은 기존과 같이 `UNCOMPUTED`로 남고, 모든 사건이 실행되었다는 뜻으로 승격하지 않는다.

## 차단 성공·실패 branch catalog

차단 성공과 실패는 같은 initiating event 뒤의 조건부 branch이므로, 각각의 provider 방출 history를 별도 `RequestBranchTemplate`으로 입력할 수 있게 했다. CLI의 `--request-branch-catalog`은 각 branch의 ID·조건부 확률·provenance·`ConsequenceRequest`를 exact-match한다. matched branch 확률이 1보다 작으면 부족한 확률을 `uncomputed-provider-branch-remainder`로 추가하고, 1보다 크면 컴파일을 거부한다. 이 규칙은 성공 history만 있는 상태에서 실패 확률을 0으로 암묵 처리하는 것을 막는다.

현재 합성 branch 단위검증은 저장탱크 `AREA_0.01%` 사건에 0.7/0.3 두 branch를 보존하고, 0.7만 제공한 경우 0.3을 미계산으로 남기는 것을 확인한다. 실제 차단 신뢰도와 실패 history가 없으면 이 기능도 시설 전체 위험을 완성하지 않는다.

## 두 설비 catalog 실행 진단

합성 provider catalog에 저장탱크 요청과 이송배관의 `ResolvedLiquidRelease` 요청을 각각 넣어 현재 pinned backend로 실행했다. 문헌 사건 10개 중 요청 연결은 2개였고, 저장탱크 1건은 `EXECUTED`, 배관 1건은 방출·확산·점화·피해까지 계산한 `EXECUTED_OPERATOR_LIMITED`였다. 나머지 8건은 요청 이력이 없어 `UNCOMPUTED`로 남았다.

두 실행 사건의 새 물리 계산시간은 약 1.66–3.76초/건, 캠페인 전체는 약 5.73초였다. 배관 사건의 provider 질량 장부 잔차는 0 kg였지만, 입력 경계와 종료조건이 합성값이고 open physical closure가 남아 있어 전체 시설 IR/F-N은 `null`이다. 이 진단은 catalog가 설비별 방출 경계를 올바르게 선택하는지 검증한 것이며, 실제 설비의 모델 정확도나 문헌 빈도 완결을 뜻하지 않는다.

## provider packet 직접 결합

이번 보완에서 `build_equipment_campaign_from_provider_catalog()`와 CLI의 `--provider-release-catalog` 경로를 추가했다. 외부 모델이 `prism.resolved_release.v1` packet을 여러 설비에 대해 제공하면 다음 순서가 한 번에 실행된다.

1. gas/liquid 또는 emergency-relief packet의 strict 경계·질량·엔탈피·시간 장부를 검증한다.
2. `request_defaults`의 weather·ignition·domain·source operator·종료근거를 packet과 결합한다.
3. 설비 ID와 실제 failure opening을 `FrequencyPlan`의 사고 크기와 exact-match한다.
4. 일치하지 않는 문헌 LOC는 기존과 같이 `UNCOMPUTED`로 보존한다.

packet이 여러 개일 때 event ID가 중복되거나 defaults의 종료시간·operator가 packet과 맞지 않으면 캠페인 자체를 만들지 않는다. 이는 부분 packet을 조용히 버리거나 다른 설비의 방출을 복사하는 것을 막기 위한 선택이다. 부분 catalog를 별도 보고서로 남겨야 할 때는 기존 `build_provider_request_catalog.py`를 먼저 사용한다.

```powershell
.venv\Scripts\python.exe lh2-tno/scripts/build_equipment_campaign.py `
  --manifest lh2-tno/examples/equipment_manifest.json `
  --frequency-plan lh2-tno/examples/equipment_frequency_plan.json `
  --provider-release-catalog provider_releases.json `
  --release-kind accidental_leak `
  --request-defaults request_defaults.json `
  --annual-conditions lh2-tno/examples/equipment_annual_conditions.json `
  --scope-provenance "reviewed provider release campaign" `
  --output equipment_campaign.json
```

비상 릴리프는 `--release-kind emergency_relief`로 별도 호출한다. 정상 벤트나 일반 흐름 JSON은 이 경로의 입력이 될 수 없다. 현재 검사센터 export에는 적격 사고·비상 릴리프 packet이 0건이므로, 이번 direct 경로도 실제 센터 위험을 산출하지 않고 자료가 들어올 때 사용할 준비 단계로 남아 있다.

## provider packet의 차단 성공·실패 branch

직접 packet 경로도 같은 initiating event 뒤의 여러 방출 이력을 보존할 수 있도록 `ProviderReleaseBranch`와 `--provider-release-branch-catalog`을 추가했다. wrapper의 `release`는 기존 `prism.resolved_release.v1` strict packet이고, wrapper는 조건부 확률과 provenance만 추가한다. 각 packet은 별도로 질량·엔탈피·종료시계·failure opening을 검증한 뒤 `RequestBranchTemplate`으로 변환된다. 이후 일반 branch compiler가 component/opening exact-match를 수행한다.

이 구조에서는 provider가 성공 packet만 내보낸 경우 누락된 실패 확률을 0으로 만들지 않는다. 확률 합이 1보다 작으면 `uncomputed-provider-branch-remainder`가 생기고, 1보다 크면 캠페인 입력을 거부한다. 합성 liquid packet을 두 wrapper로 감싼 CLI smoke test에서 10개 LOC 중 정확히 맞는 1개 사건에 2개 branch가 연결되고 나머지 9개 LOC는 미계산으로 남았다. 이는 실제 barrier 신뢰도나 센터 사고 이력이 아니며, 실제 provider packet이 들어왔을 때 동일한 경로를 재사용하기 위한 계약 검증이다.

새 단위검증을 포함한 portable suite는 **281개 통과**했다. 이는 adapter와 컴파일러의 계약 검증이며, 실제 설비 물리 검증이나 전체 시설 QRA 완료를 의미하지 않는다.

합성 liquid packet으로 direct CLI를 실행한 캠페인은 `results/20261009/direct_provider_liquid_campaign.json`에 저장했다. 10개 문헌 LOC 중 저장탱크의 실제 개구와 맞는 1개만 연결되고 9개는 `UNCOMPUTED`로 남았다. 이어서 이 캠페인을 현재 pinned backend로 실제 실행해 `results/20261009/direct_provider_liquid_campaign_result.json`에 결과를 저장했다. 연결된 1건은 방출→SLABx-LH2 확산→점화→피해→수용점 known contribution까지 계산되었고 새 물리 계산은 약 1.66초, 전체 캠페인은 약 1.85초였다. 다만 source operator의 constant-state/open physical closure 한계 때문에 `EXECUTED_OPERATOR_LIMITED`이며, 9건은 미계산으로 남고 전체 시설 IR/F-N은 `null`로 보류된다. 따라서 이 실행은 direct packet 경로가 시설 위험 실행기에 도달한다는 것을 검증한 것이며 실제 시설 QRA나 물리 검증 완료를 뜻하지 않는다.

## 설비별 campaign의 시설 ledger 결합

설비 모델이 탱크·배관·밸브별로 별도 campaign 결과를 내보내는 경우를 위해 `src/lh2_tno/facility_ledger.py`와 `scripts/merge_facility_campaigns.py`를 추가했다. 이 단계는 방출이나 SLABx 계산을 다시 수행하지 않고, 각 campaign이 이미 만든 risk atom을 시설 수용점별 IR과 expected-death F-N으로 합친다.

결합 전에 전체 시설 component ID 목록을 명시하고 다음을 검사한다.

- event ID와 asset 소유권이 campaign 사이에서 중복되지 않는지 확인한다.
- 모든 risk atom의 수용점, 빈도, 조건부 가중치, 피해 endpoint가 유한하고 서로 닫히는지 확인한다.
- 기대 설비 ID가 모두 들어왔는지 확인하고, 누락 설비는 0 위험으로 바꾸지 않는다.
- 입력 campaign의 `UNCOMPUTED`, 제외 설비, 합성 방출시계, 부분 component가 남으면 시설 total을 보류한다.
- 필요한 주요 사고 scope matrix 행이 모두 `EXECUTED`인지 확인한다.

조건이 충족되면 `FACILITY_SCOPE_EXECUTED`와 `total_facility_*`를 출력하고, 그렇지 않으면 `PARTIAL_FACILITY_SCOPE`와 known contribution만 출력한다. 합성 inventory campaign 한 건으로 실행한 smoke test는 5개 event, 4개 수용점, 전체 위험 사용 가능 상태를 만들었지만, 이 결과는 물리 검증이나 실제 시설 packet의 대체가 아니다. 실제 사고 packet·설비 범위·독립 검증이 채워질 때 같은 ledger를 최종 시설 결합에 사용한다.
