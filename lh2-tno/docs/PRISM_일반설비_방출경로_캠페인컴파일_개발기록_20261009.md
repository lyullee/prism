# PRISM 일반 설비 방출경로 캠페인 컴파일 기록

2026-10-09. 일반 설비 매니페스트, 문헌 `FrequencyPlan`, 방출 요청 템플릿과 연간 기상·인구 조건을 하나의 `RiskCampaign`으로 컴파일하는 경로를 추가했다.

## 연결 방식

`src/lh2_tno/campaign_template.py`의 컴파일러는 먼저 매니페스트가 `EXECUTABLE`인지 확인한다. 이어서 `generate_events()`가 만든 모든 문헌 LOC를 순회한다.

- 설비 ID와 방출 개구가 요청 템플릿과 일치하면 요청을 캠페인 템플릿으로 보존한다.
- 캠페인 실행 시에만 해당 사건의 빈도와 현재 기상 조건을 바인딩한다.
- 개구가 다르거나 설비가 다르면 크기를 바꾸거나 다른 설비 요청을 재사용하지 않고 `UNCOMPUTED` 사유를 만든다.
- 컴파일 단계는 물리 backend를 실행하지 않는다.

실행 명령은 다음과 같다.

```powershell
.venv\Scripts\python.exe lh2-tno/scripts/build_equipment_campaign.py `
  --manifest lh2-tno/examples/equipment_manifest.json `
  --frequency-plan lh2-tno/examples/equipment_frequency_plan.json `
  --request-template lh2-tno/examples/equipment_consequence_template.json `
  --annual-conditions lh2-tno/examples/equipment_annual_conditions.json `
  --scope-provenance "synthetic generic manifest campaign" `
  --output equipment_campaign.json
```

## 합성 예제 결과

예제 FrequencyPlan은 저장탱크 5개 area-bin과 이송배관 5개 area-bin을 생성한다. 요청 템플릿의 개구는 저장탱크 `AREA_0.01%`와만 일치하므로 컴파일 결과는 **10개 사건, 요청 연결 1개, 미계산 9개**다.

이 캠페인을 현재 pinned backend로 실행한 진단에서는 저장탱크 사건 1건이 방출→확산→점화→피해→수용점 IR/F-N까지 실행되었고, 9건은 `UNCOMPUTED`로 남았다. 실행된 사건의 새 물리 계산 시간은 약 3.77초, 전체 캠페인은 약 4.14초였다. known contribution IR은 합성 수용점에서만 기록했고, 전체 시설 IR/F-N은 `null`로 유지했다.

## 해석 한계

예제의 탱크 상태·방출 지속시간·점화확률·인구·기상은 합성값이다. 컴파일러가 `EXECUTABLE` 캠페인을 만들었다는 사실은 실제 설비의 provider 방출 이력이나 현장 신뢰도를 증명하지 않는다. 검사센터 자료는 아직 `PARTIAL`이므로 이 경로에 실제 센터 결과를 넣어 시설 위험으로 승격하지 않았다.

다음 승격 조건은 실제 설비별 provider 방출·차단·재고 소진 이력, 실제 포트와 수용점, 검토된 점화·인구·기상 조건을 동일한 계약으로 제공하는 것이다. 하나라도 빠지면 현재처럼 사건별 미계산과 known contribution을 분리한다.

## 복수 설비 방출 요청 catalog

실제 옥외 시설은 탱크, 이송배관, 밸브 또는 다른 설비마다 서로 다른 provider 방출 경계를 가질 수 있다. `build_equipment_campaign_from_catalog()`와 CLI의 `--request-catalog`은 여러 `ConsequenceRequest`를 한 번에 받아 빈도 사건별로 선택한다. 선택 조건은 요청의 `component_id`와 provider가 선언한 실제 failure opening이다. 개구가 다른 요청을 크기만 바꾸어 재사용하지 않으며, 같은 사건에 두 요청이 맞으면 모호성 오류를 낸다.

이 기능은 설비별 결합을 위한 컴파일 단계다. 실제 설비 모델이 방출 이력·위치·상·지속시간·종료 장부를 제공하지 않는 상태에서 물리 계산을 대신하지 않는다. 요청 catalog에 없는 사건은 기존과 같이 `UNCOMPUTED`로 남고, 모든 사건이 실행되었다는 뜻으로 승격하지 않는다.

## 두 설비 catalog 실행 진단

합성 provider catalog에 저장탱크 요청과 이송배관의 `ResolvedLiquidRelease` 요청을 각각 넣어 현재 pinned backend로 실행했다. 문헌 사건 10개 중 요청 연결은 2개였고, 저장탱크 1건은 `EXECUTED`, 배관 1건은 방출·확산·점화·피해까지 계산한 `EXECUTED_OPERATOR_LIMITED`였다. 나머지 8건은 요청 이력이 없어 `UNCOMPUTED`로 남았다.

두 실행 사건의 새 물리 계산시간은 약 1.66–3.76초/건, 캠페인 전체는 약 5.73초였다. 배관 사건의 provider 질량 장부 잔차는 0 kg였지만, 입력 경계와 종료조건이 합성값이고 open physical closure가 남아 있어 전체 시설 IR/F-N은 `null`이다. 이 진단은 catalog가 설비별 방출 경계를 올바르게 선택하는지 검증한 것이며, 실제 설비의 모델 정확도나 문헌 빈도 완결을 뜻하지 않는다.
