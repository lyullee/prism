# 검사센터 상태신호의 일반 설비 클래스 매핑

검사센터의 인수·저장벤트·공급 시계열 3개는 `examples/inspection_center_observed_state_evidence.json`에 상태 증거로 보존되어 있다. 이 자료만으로는 실제 자산번호, P&ID 끝점, 누출 개구부, 사고 빈도, 방출 packet을 확정할 수 없다.

이번 단계에서는 상태 신호가 **어떤 종류의 일반 액화수소 설비 모델에 후보로 들어갈 수 있는지**만 별도 장부로 만들었다.

```powershell
python scripts/audit_observed_component_mapping.py `
  --observed-state-evidence examples/inspection_center_observed_state_evidence.json `
  --mapping-manifest examples/inspection_center_observed_component_mapping_manifest.json `
  --output results/20261026/native_full_scope_union_assessment/observed_component_mapping_audit.json
```

결과는 `prism.observed_component_mapping_audit.v1`이며 현재 3개 후보 매핑을 기록한다.

| 관측 component | 후보 일반 모델 | 현재 후보 alias | 현재 판정 |
|---|---|---|---|
| `lh2-intake-tank` | `storage_tank` | TK-1101, TK-1102, TANK1, TANK2 | 후보 클래스만 |
| `lh2-storage-vent` | `storage_tank_operating_vent_path` | XV10, XV11 | 후보 클래스만 |
| `lh2-supply-vaporizer-boundary` | `vaporizer_supply_boundary` | VP-1101 | 후보 클래스만 |

현재 결과의 상태는 `CANDIDATE_COMPONENT_CLASS_MAPPINGS_ONLY`다. `facility_component_id`는 모두 비어 있고, 정확한 자산 식별과 provider event 연결은 열리지 않는다. 따라서 이 장부는 디지털트윈의 센서 입력을 일반 설비 모델 후보에 배치하는 데는 사용할 수 있지만, 누출 시나리오·빈도·방출 지속시간·SLABx-LH2 피해·시설 IR/F-N을 계산하거나 승격하지 않는다.

실제 자산대장과 P&ID crosswalk가 확보되면 `review_status=field_confirmed`, `facility_component_id`, `asset_identity_evidence_refs`를 함께 제출할 수 있다. 이 경우 감사 결과는 `EXACT_COMPONENT_MAPPINGS_NO_RELEASE` 또는 후보와 확정이 섞인 `MIXED_COMPONENT_MAPPINGS_NO_RELEASE`로 바뀌지만, provider 방출 이벤트가 없으면 여전히 사고 계산과 빈도 연결은 열리지 않는다.

다음에 필요한 자료는 최종 자산대장, P&ID의 계측·밸브·벤트 끝점 crosswalk, 설비별 상태 snapshot 계약, 그리고 동일 component/event를 가리키는 적격 provider release packet이다. 이 자료가 들어오면 별도의 `observed_state_release_binding_manifest`에서 exact facility component와 provider event를 검토하고, 현재 fail-closed binding 감사와 연결한다.
