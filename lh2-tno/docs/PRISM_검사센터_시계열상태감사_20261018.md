# PRISM 검사센터 시계열 상태 감사

2026-10-18 기준으로 `액화수소검사지원센터 데이터`의 XLSX 시계열을 일반 LH2 시설 모델에 바로 연결하지 않고, 실시간 상태 입력 후보로서 먼저 감사했다. 이 단계의 목적은 센터에 맞춘 고정 모델을 만드는 것이 아니라, 다른 LH2 시설에서도 같은 파일·태그·단위 검사를 재사용할 수 있게 하는 것이다.

## 실행

```powershell
python scripts/audit_inspection_center_timeseries.py `
  --source-root "C:\Users\lyul\Desktop\DocuData\액화수소검사지원센터 데이터" `
  --output results/20261018/inspection_center_timeseries_audit.json `
  --summary-output examples/inspection_center_timeseries_audit.json
```

검사기는 XLSX 파일의 SHA-256, 시트 수, 헤더, 행 수, 태그 접두어 기반 신호 종류, 집계된 최소·최대·개수만 저장한다. 원본 행과 원시 시계열은 PRISM 저장소에 복사하지 않는다. 읽기 오류는 파일·시트 수준에서 남기고 전체 감사를 중단하지 않는다.

## 현재 확인 결과

현재 데이터 폴더에서 17개 workbook과 78개 sheet를 읽었다. 압력(`PT`), 차압(`DPT`), 온도(`TT`) 후보 태그를 찾았고, 실제 숫자값이 하나라도 있는 522개 후보 수치 열의 공학 단위가 파일 헤더 또는 별도 검토 자료로 확인되지 않았다. 따라서 숫자 범위만으로 bar, K, %, kg/s 등을 추정하지 않는다.

상태는 `SCREENING_ONLY_UNIT_BASIS_UNCONFIRMED`다. 이 상태에서 검사기는 다음을 모두 거짓으로 고정한다.

- `state_snapshot_binding_allowed`
- `frequency_applied`
- `sensor_frequency_learning_used`
- `provider_packet_created`
- `facility_qra_claim`

이렇게 해야 검사센터의 운전 데이터가 우연히 문헌 빈도나 사고 방출 packet으로 잘못 승격되지 않는다. 시계열은 공정 상태의 후보 증거이지, 사고 발생 빈도 자체가 아니다.

## 다음 연결 조건

상태 입력으로 사용하려면 설비·포트·태그의 대응표, 단위와 기준(절대압/게이지압, K/°C, 질량유량 기준), 보정·결측·시각 품질, 샘플링 지연을 검토한 JSON map이 필요하다. `--unit-map`은 이 검토 결과를 exact tag-to-unit으로 받지만, 단위 map만 제공해도 자동으로 사고 packet이나 시설 QRA를 만들지는 않는다. 이후 별도의 state-snapshot adapter와 설비별 사고 export가 exact-match를 통과해야 한다.

공개 요약은 `examples/inspection_center_timeseries_audit.json`, 원본 경로와 전체 감사 결과는 로컬 `results/20261018/inspection_center_timeseries_audit.json`에 있다. 공개 요약은 상대 경로와 해시·집계만 포함하며, 특정 검사센터의 설비 구성을 일반 시설의 기본값으로 사용하지 않는다.

## 명시적 행→텔레메트리 프레임 어댑터

일반 설비 모델이나 검토자가 별도 확인한 표 형식의 한 행을 실시간 입력으로 넘길 때는 `lh2_tno.inspection_timeseries.frame_from_row()`를 사용한다. 이 함수는 검사센터 전용 태그를 코드에 넣지 않고, 호출자가 각 원본 열에 대해 `tag`, `unit`, `quality`를 명시한 바인딩을 넘기도록 한다.

```python
from lh2_tno.inspection_timeseries import frame_from_row

frame = frame_from_row(
    {"PT_101": 2.1e5, "TT_101": 22.0},
    stream_id="tank-01",
    sequence=10,
    source_time_s=1700000000.0,
    arrival_time_s=1700000000.2,
    origin="historian_measured",
    bindings={
        "PT_101": {"tag": "tank-01.pressure", "unit": "Pa", "quality": "valid"},
        "TT_101": {"tag": "tank-01.temperature", "unit": "K", "quality": "valid"},
    },
)
```

바인딩에 단위·품질·태그가 없거나, 원본 열이 없거나, 값이 유한한 숫자가 아니면 즉시 실패한다. 함수는 압력 단위·온도 단위·질량유량을 추정하지 않고, 시간·스트림·원점도 호출자가 제공한 값을 그대로 엄격히 검사한다. 이 프레임은 공정 상태 입력만 표현하며 사고 방출 소유권, 방출 지속시간, 사고 빈도 또는 provider 자격을 만들지 않는다. 따라서 이 어댑터가 성공해도 `state_snapshot_binding_allowed`, 빈도 적용, provider packet, 시설 IR/F-N 승격은 별도 계약과 증거가 없으면 계속 닫혀 있다.

정규화된 프레임을 설비 상태로 넘길 때는 `state_snapshot_from_row()`를 사용할 수 있다. 이 함수는 기존 `TelemetryNormalizer`에 단위 변환, 압력 기준, 센서 위치, 품질, 최신성, 순서 검사를 맡긴 뒤 `EquipmentStateSnapshot`만 만든다. 여러 압력·온도 태그가 있으면 `pressure_tag`와 `temperature_tag`를 명시해야 하며, 정규화 실패는 provider 호출 전에 중단된다. snapshot에는 누출구경, 방출시간, 종료근거, 사고빈도, provider 방출을 넣을 수 없고, snapshot digest가 맞는 별도 사고 export 요청이 있어야 다음 단계로 이동한다.

실시간 모니터에서 같은 경계를 한 번에 사용하려면 `RealtimeConsequenceMonitor.update_from_row()`에 행과 명시적 바인딩을 넘긴다. 내부에서는 먼저 `frame_from_row()`가 엄격한 `Frame`을 만들고, 그 뒤 기존 `update_from_frame()`이 정규화·provider resolver·피해 계산·deadline 장부를 수행한다. 바인딩이 빠지거나 단위가 틀리면 이 경계에서 중단되며, 정상 행의 값으로 누출 크기나 빈도를 추정하지 않는다.

시설 단위에서는 `FacilityRealtimeConsequenceMonitor.update_from_rows()`가 모든 선언 컴포넌트의 행과 메타데이터를 한 배치로 받는다. 행·메타데이터의 컴포넌트 집합이 선언 설비와 정확히 같아야 하며, 각 설비의 stream·sequence·source/arrival time·origin·열 바인딩을 따로 명시한다. 이 검사를 통과한 뒤에만 기존 `update_from_frames()`가 실행되므로 한 설비의 행이 빠진 상태로 시설 결과를 조용히 합산하지 않는다.

행이 잘못되면 함수는 `REJECTED` 배치와 `row_input_errors`, `missing_row_components`, `missing_row_metadata_components`를 반환한다. 해당 컴포넌트는 결과 합산에서 제외되고 0 위험값으로 대체되지 않는다. 추가 설비 행도 `unknown_frame_components`로 남기므로 입력 집합이 달라진 사실을 운영자가 확인할 수 있다.

### 시설 배치의 시간창과 전체 연결 확인

시설 배치가 `ACCEPTED`여도 각 설비의 원본 시각이 완전히 같은 시각이라는 뜻은 아니다. `update_from_frames()`와 `update_from_rows()`는 이제 accepted 컴포넌트의 `source_time_s`와 `arrival_time_s`의 최소값·최대값·범위를 `aggregate.facility_time_window`에 남긴다. 예를 들어 두 설비의 원본 시각 차이가 1.5초이면 `source_time_span_s=1.5`로 기록한다. PRISM은 이 값을 보고만 하며, 임의의 보간·재표본화·이전 결과 재사용으로 시설 시각을 맞추지 않는다. 따라서 `coherence_asserted`는 현재 항상 `false`이고, 운영 화면이나 상위 디지털트윈이 허용 시간창을 별도로 판단해야 한다.

운영자가 허용 원본 시각 범위를 PRISM에서 강제해야 하면 `FacilityRealtimeConsequenceMonitor(max_source_time_span_s=...)`를 사용한다. 값이 양수로 선언된 경우 완전한 설비 배치의 `source_time_span_s`가 범위를 넘으면 `time_window_rejection.status=REJECTED_SOURCE_TIME_WINDOW`로 닫고 시설 IR/F-N 합산을 수행하지 않는다. 실패한 개별 결과는 원인 분석을 위해 남지만 시설 합계에는 들어가지 않는다. 값을 생략하면 시간창을 측정만 하는 호환 모드이며, 두 모드 모두 시각을 자동 보간하지 않는다.

행 배치에 `release_resolver`가 선언된 설비가 있으면 연결은 다음 순서로 실행된다.

`행 + 명시적 단위/태그` → `Frame` → `TelemetryNormalizer` → `equipment process state` → `provider release resolver` → `방출 지속시간·차단/종료·재고 장부` → `SLABx-LH2/TNO 피해계산` → `시설 배치 장부`.

이 경로의 회귀 테스트는 `test_facility_realtime_monitor_row_batch_connects_state_to_provider_release_and_consequence`에 있다. 테스트는 상태 압력값이 resolver에 도달한 뒤 provider 사고 ID, 0.2초 방출시간, 잔여 재고 0.8 kg, 합성 진단 지평선 차단 상태가 시설 결과에 함께 기록되는지 확인한다. 테스트의 provider packet은 합성 예시이므로 qualified 실제 설비 증거로 승격되지 않으며, 시설 연간 IR/F-N 게이트도 계속 닫혀 있다.

`RealtimeFrequencyBinding`과 `RealtimePopulationBinding`을 행 배치에 추가하면 `current_weather_annual_ir_low_high`와 조건부 expected-death F/N이 여러 설비의 accepted 결과에서 합산된다. 이 계산은 검토된 문헌 빈도와 명시 인구를 곱한 현재 기상 조건부 결과이며, 빈도를 센서에서 학습하지 않는다. `facility_annual_risk_available`와 `facility_fn_available`은 계속 `false`이고, 전체 시설의 사고범위·qualified provider·물리검증 gate를 통과하기 전에는 연간 시설 QRA로 해석하지 않는다. `test_facility_row_batch_combines_literature_ir_and_conditional_fn`이 이 경로와 빈도 민감도 장부를 검증한다.

빈도 입력은 수동 숫자 복사보다 패키지 카탈로그의 `FrequencyEvent`를 직접 연결하는
`RealtimeFrequencyBinding.from_frequency_event()`를 사용할 수 있다. 이 helper는
`generate_events()`가 만든 Purple/LH2 사건의 ID·연간 빈도·문헌 SHA-256·p05/p95를
보존한다. 가동조건·방출분기·재실 확률은 사건의 물리 빈도와 별도의 조건이므로
호출자가 모두 명시해야 한다. 조건을 센서에서 추정하거나 사건 개구가 provider
방출 경계와 맞지 않을 때는 binding을 만들지 않고 risk atom을 보류한다.
이 계약은 `test_realtime_frequency_binding_uses_packaged_catalogue_event`에서
카탈로그 사건과 조건부 가중치 산술까지 확인한다.

시설 배치 결과의 `aggregate.processing_time`은 accepted 설비별 서비스 경과시간과
provider 물리계산 경과시간을 합계·평균·최대값으로 집계한다. 이 값은 한 번의
동기 배치 측정이며 지속 처리량이나 fresh physics 1 Hz를 의미하지 않는다. 부분
배치나 잘못된 시간 값은 `AVAILABLE_PARTIAL_BATCH` 또는 `WITHHELD`로 남겨, 운영
화면이 누락 시간을 0으로 해석하지 않게 한다.
