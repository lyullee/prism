# PRISM 실시간 공정상태와 사고 방출 경계 계약

작성일: 2026-10-09
상태: 구현·검사 완료, 실제 설비 승격은 보류

## 왜 이 경계가 필요한가

디지털트윈은 평상시 설비 상태를 계속 계산합니다. 예를 들면 압력, 온도, 액면, 질량유량, 상 상태, 밸브 명령과 같은 값입니다. 이 값은 **현재 설비가 어떤 상태인지** 알려 주지만, 그 자체가 사고 방출을 뜻하지는 않습니다.

사고 방출에는 별도의 판단이 필요합니다.

1. 어떤 사고가 시작됐는지(예: 배관 LOC, 밸브 고장, 비상 릴리프).
2. 실제 개구와 방향이 무엇인지.
3. 얼마 동안 얼마나 방출되는지.
4. 재고 소진 또는 차단으로 언제 끝나는지.
5. 문헌 빈도를 어떤 사건에 붙일지.

이 판단은 설비 공정 모델/provider가 계산하고 `ConsequenceRequest`의 `ResolvedGasRelease`, `ResolvedGasReleaseSet`, 또는 `ResolvedLiquidRelease`로 내보냅니다. PRISM은 이 경계를 받은 뒤에만 SLABx-LH2/SLABx, 점화, 화재·폭발, 인명 피해를 계산합니다.

## 구현된 흐름

```text
정상 공정 상태 snapshot
        │  (단위·시간·품질을 TelemetryNormalizer가 확인)
        ▼
validate_equipment_process_state
        │  (사고 packet·빈도·개구·지속시간 필드가 섞였으면 거절)
        ▼
외부 LH2 설비 resolver/provider
        │  (설비별 사고 방출 이력과 종료 근거를 계산)
        ▼
ConsequenceRequest의 provider release boundary
        │  (source_input·빈도·센서 역추정은 함께 사용하지 않음)
        ▼
SLABx-LH2/SLABx → 점화·화재/폭발 → 인명 피해 → 조건부 위험
```

`RealtimeConsequenceMonitor`는 이 흐름을 한 프레임 단위로 실행하고 입력 나이, 계산 시간, cache hit/fresh physics, deadline을 기록합니다. deadline을 넘겨도 이전 결과를 새 결과처럼 표시하지 않습니다.

## 실시간 피해에 문헌 빈도를 붙이는 방법

`FacilityRealtimeBinding`에 선택적으로 `RealtimeFrequencyBinding`을 지정할 수 있습니다. 이 binding은 센서 frame과 별도의 검토 자료이며, 사건 ID·자산 ID·문헌 개시빈도·현재 기상확률·방출분기확률·재실확률·출처 문구·SHA-256을 함께 갖습니다. `FacilityRealtimeConsequenceMonitor`는 provider consequence 결과의 `harm_given_observed_release_low_high`를 확인한 뒤 다음처럼 현재 기상 IR만 계산합니다.

```text
문헌 개시빈도
× 현재 기상 조건 확률
× 방출 branch 확률
× 재실확률
× provider 피해확률
= current_weather_annual_ir_low_high
```

수용점 피해가 없거나 빈도 binding이 빠진 설비는 `WITHHELD`로 남깁니다. 이 경로는 센서에서 빈도를 학습하지 않고 누출 크기를 역추정하지 않습니다. 인구별 기대 사망자와 여러 기상·사고 family 전체가 한 snapshot에 들어오지 않으므로 F/N과 시설 전체 annual IR은 계속 보류합니다. 이 값은 문헌 빈도와 현재 frame의 조건부 결합이 실제로 계산됐는지를 보여주는 진단 결과입니다.

문헌에 p05/p95 경계가 함께 있으면 `RealtimeFrequencyBinding`에 두 값을 추가할 수 있습니다. monitor는 같은 피해 결과를 다시 실행하지 않고 p05·published·p95의 현재 기상 IR을 재가중해 `current_weather_frequency_sensitivity_ir_low_high`에 기록합니다. 이 표본은 빈도 민감도이며 새로운 고장률 분포를 만들거나 시설 credible interval을 주장하지 않습니다. p05·p95 중 하나만 있거나 published 값의 양쪽에 놓이지 않으면 binding을 거절합니다.

## 상태 snapshot에서 허용되는 것

`values` 안에는 `value_si`가 있는 유한한 설비 상태 값이 들어갑니다. 압력·온도·액면·질량유량·수소농도·차압 등은 허용되며, 외부 provider가 사용하는 상·운전·제어 메타데이터도 상태 설명으로 포함할 수 있습니다. 값은 SI로 정규화된 숫자여야 합니다.

상태 snapshot에는 다음을 넣지 않습니다.

- 누출 구멍 직경·면적과 같은 사고 개구
- 방출 단계(`steps`), 방출 기간, 누적 방출 질량
- `Resolved*Release` packet 또는 provider export schema
- 사건 ID·사건 종류·방출 종료 근거
- 연간 빈도, initiation intensity, frequency event

이 항목을 snapshot 안에 넣으면 `validate_equipment_process_state()`가 경로를 표시하며 즉시 거절합니다. resolver에는 원본을 직접 넘기지 않고 검증된 깊은 복사본을 넘기므로 resolver가 상태를 바꿔도 입력 snapshot이 변하지 않습니다.

## 실제 설비 연결 방법

외부 LH2 공정 모델은 정상 상태와 사고 방출 결과를 분리해 export해야 합니다.

```python
from lh2_tno.service import request_from_equipment_resolver

request = request_from_equipment_resolver(
    template,
    normalized_process_state,
    lambda template, state: equipment_model.resolve_accident_release(
        template.component_id, state
    ),
)
```

resolver가 반환하는 request는 다음을 모두 만족해야 합니다.

- template와 component ID가 일치한다.
- provider 방출 경계가 정확히 하나 있다.
- `source_input`을 섞지 않는다.
- 빈도를 새로 지정하지 않는다. 빈도는 문헌 `FrequencyPlan`에서 별도로 exact-match한다.
- `release_termination`이 명시돼 있다.

이 계약을 만족하지 못하면 피해 계산으로 넘어가지 않고 `ValueError`로 중단합니다. 정상 운전 유량이나 검사센터 시계열을 사고 방출로 자동 변환하지 않습니다.

## 현재 상태와 남은 작업

코드 경계와 fail-closed 검사는 구현됐고 portable 검사에 포함됐습니다. 그러나 현재 외부 LH2 디지털트윈 screening 자료에는 확정 센터 자산과 사고 `Resolved*Release` packet이 없으므로, 일반 시설 전체 QRA로 승격할 수 없습니다. 다음 필수 입력은 설비별 사고 packet catalog, 포트·방향·종료 근거, 그리고 같은 사고 가족에 exact-match되는 문헌 빈도입니다.
