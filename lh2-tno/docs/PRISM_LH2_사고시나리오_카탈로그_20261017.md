# PRISM LH2 사고 시나리오 카탈로그

이 문서는 PRISM이 액화수소 시설에서 계산 대상으로 선언한 야외 주요사고를 한 곳에서 관리하는 방법을 설명한다. 카탈로그는 사고 결과를 만들어 내는 계산기가 아니다. 설비 모델, 빈도 계획, 사고 방출 provider, SLABx-LH2/TNO 피해 계산이 어떤 조건으로 연결되어야 하는지를 고정하는 계약이다.

## 카탈로그가 필요한 이유

액화수소 시설은 탱크 하나만 계산하면 끝나지 않는다. 탱크, 이송 배관, 밸브, 펌프, 벤트·안전밸브, 기화기, 재액화기를 각각 사고 시작점으로 볼 수 있다. 또한 같은 설비라도 작은 구멍, 재고가 모두 빠지는 경우, 600초 동안 계속되는 경우, 배관 양단이 동시에 열리는 경우는 방출 시간이 다르다.

PRISM은 이 차이를 다음 순서로 추적한다.

`설비 종류 → 사고 시나리오 family → 빈도 event → provider 방출 packet → 종료·질량 ledger → SLABx-LH2/TNO 피해 → 점화·IR/F-N`

카탈로그의 각 행에는 다음 항목이 들어 있다.

- 적용 설비 종류
- 허용 방출 모드
- 필요한 provider packet schema
- 방출 종료 근거
- 허용 source operator
- 최종 피해 계산으로 이어지는 경로
- packet이 아직 없을 때 표시할 미계산 사유

따라서 “이벤트가 만들어졌다”와 “실제 방출부터 시설 위험까지 계산됐다”를 구분할 수 있다.

## 빈도 worklist와의 연결

`build_provider_release_worklist()`는 각 frequency event에 `scenario_families`를 붙인다. 예를 들어 저장탱크 `hole` event는 `vessel_hole`과 `liquid_two_phase`를 함께 요구하고, 배관 양단 파열은 `two_sided_rupture`만 요구한다. 이 정보는 빈도를 새로 만드는 값이 아니다. 이미 선언된 event가 어떤 provider packet과 어떤 종료 ledger를 받아야 하는지 표시하는 연결표다.

worklist의 `scenario_family_counts`는 family별 요청 개수를 보여준다. 요청 개수가 있어도 provider packet이 없으면 상태는 `UNCOMPUTED_PROVIDER_PACKET`으로 남는다. `scenario_families`가 비어 있는 event는 카탈로그와 연결되지 않은 설정 오류로 취급해야 하며, 수동으로 다른 family에 대체해서는 안 된다.

`build_accident_scope_matrix.py --provider-worklist ...`를 사용하면 worklist event ID와 campaign event ID, 주 사고 family가 일치하는지도 확인한다. 최신 generic 24-event 진단에서 이 구조 검사는 `ALIGNED`였지만, provider packet 수는 0건이고 실제 facility QRA 승격은 되지 않았다. 즉 구조가 맞는 것과 물리 증거가 확보된 것은 별도 조건이다.

IJHE 완료 감사도 이 alignment 결과를 진단용 PASS 항목으로 기록한다. alignment PASS는 worklist와 campaign의 구조가 맞다는 뜻이고, 실제 packet 자격·물리 검증·시설 전체 IR/F-N의 PASS로 해석되지 않는다.

campaign이 생성한 risk atom에는 `scenario_families`가 보존되고, 시설 ledger에는 `scenario_family_contributions`가 기록된다. 이 값은 같은 risk atom을 설비 family와 액체 2상 family에서 각각 볼 수 있게 하는 분석용 분해다. 겹치는 family의 IR/F-N을 다시 더하면 안 된다. 실제 시설 합산은 risk atom을 한 번만 사용하고, family 표는 원자에 대한 분류별 조회로만 사용한다.

문헌 빈도 불확실성 모듈도 같은 분류를 사용한다. 각 p05·published·p95 시나리오에는 `scenario_family_known_expected_fatalities_low_high`와 `scenario_family_rank_by_known_expected_fatalities_low_high`가 추가된다. 로그정규 sampling을 사용할 때는 `scenario_family_rank_stability`가 추가된다. 이 값은 물리를 재실행하지 않고 저장된 risk atom의 빈도만 바꾼 결과이며, 미계산 사고를 0으로 만들지 않고 시설 credible interval을 주장하지 않는다.

## 현재 선언된 12개 family

| family | 대상 설비 | 핵심 packet/종료 조건 |
|---|---|---|
| `vessel_hole` | 저장탱크 | `resolved_release.v1`, provider 종료 또는 압력 평형 |
| `pipe_hole` | 이송 배관 | `resolved_release.v1`, 실제 배관 방출 이력 |
| `valve_hole` | 밸브 | 밸브 상태와 upstream 재고를 반영한 방출 이력 |
| `vent_hole` | 벤트·안전밸브 | relief 최대 방출과 `emergency_relief_discharge` |
| `pump_hole` | 펌프 | seal/casing 사고 방출과 종료 이력 |
| `vaporizer_hole` | 기화기 | 상·하류 상태와 상변화가 반영된 방출 |
| `reliquefier_hole` | 재액화기 | weak-shell/라인 방출과 종료 이력 |
| `liquid_two_phase` | 액체가 있는 설비 | 액체 질량·밀도·엔탈피와 2상 source |
| `inventory_depletion` | 유한 재고 설비 | 재고가 0이 되는 시점의 질량 수지 |
| `inventory_over_600s` | 유한 재고 설비 | 정확히 600초 방출 이력과 질량 수지 |
| `two_sided_rupture` | 배관·밸브 | 두 endpoint packet과 공동 재고 종료 |
| `vertical_handoff` | 수직 벤트·배관·밸브 | 수직 jet 상태에서 수평 SLABx handoff |

`liquid_two_phase`, `inventory_depletion`, `inventory_over_600s`는 설비별 구멍 family와 겹칠 수 있다. 따라서 행의 빈도를 단순히 더하면 안 되고, 하나의 frequency event가 어떤 물리 경로를 택했는지 event와 branch에서 확인해야 한다.

## 현재 개발 상태와 해석

카탈로그 자체는 코드로 구현되어 scope matrix에 함께 기록된다. `scripts/export_accident_scenario_catalog.py`를 실행하면 논문 표에 사용할 수 있는 JSON을 만들 수 있다. 설비 manifest를 함께 주면 각 family에 적용되는 설비 ID도 자동으로 표시된다.

현재 외부 LayeredTank 모델에 대해서는 상태 snapshot을 provider 요청에 연결하고, provider가 동일 digest를 되돌려 주는지 확인하는 smoke가 끝났다. 이 결과는 설비 상태가 올바른 요청에 들어갔다는 증거다. 합성·operator-limited 방출은 여전히 실제 사고 packet이나 물리 검증으로 승격되지 않는다.

현재 scope matrix에서 `NO_EVENT_GENERATED`, `NO_CASE_EXECUTED`, `UNCOMPUTED`, `EXECUTED_OPERATOR_LIMITED`가 보이면 해당 family는 시설 전체 위험도에 자동 포함되지 않는다. provider packet, 종료 ledger, 물리 검증이 확보되어야 그 family를 계산 범위에 포함할 수 있다.

## 실행 예

```powershell
& "$env:PRISM_PYTHON" scripts/export_accident_scenario_catalog.py `
  --equipment-manifest examples/generic_lh2_full_scope_manifest.json `
  --output results/20261017/accident_scenario_catalog.json
```

환경변수가 없다면 PRISM 의존성이 설치된 Python으로 같은 명령을 실행하면 된다. 출력의 `physical_validation_claim`은 항상 `false`이며, 이는 카탈로그가 증거를 대신하지 않는다는 뜻이다.
