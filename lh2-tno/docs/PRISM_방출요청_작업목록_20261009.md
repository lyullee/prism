# PRISM 일반 LH2 방출 요청 작업목록

이 문서는 문헌 빈도 사건과 설비 digital twin의 방출 결과 사이의 빈칸을 명시적으로 관리한다. `provider_worklist.py`는 빈도 사건을 1건씩 읽어 어떤 방출 packet이 필요한지 적지만, 유량·지속시간·차단 성공률·재고·엔탈피를 추정하지 않는다.

## 실행 결과

```powershell
$env:PYTHONPATH = "src"
python scripts/build_provider_release_worklist.py `
  --manifest examples/generic_lh2_full_scope_manifest.json `
  --frequency-plan examples/generic_lh2_full_scope_frequency_plan.json `
  --model-binding examples/generic_lh2_model_binding.json `
  --output results/20261009/provider_evidence/generic_lh2_provider_release_worklist.json
```

현재 합성 일반 LH2 범위는 다음을 반환한다.

| 항목 | 결과 |
| --- | --- |
| 빈도 initiating event | 24건 |
| provider packet | 0건 |
| 작업목록 상태 | `READY_FOR_PROVIDER_PACKETS` |
| 각 사건 상태 | `UNCOMPUTED_PROVIDER_PACKET` |
| 모델 결합 상태 | `STATE_ONLY_BOUND`; 사고 release export 지원 부품 0개 |

이 작업목록은 `build_equipment_campaign.py --provider-worklist-only`로
`RiskCampaign`에도 넣을 수 있다.

```powershell
python scripts/build_equipment_campaign.py `
  --manifest examples/generic_lh2_full_scope_manifest.json `
  --frequency-plan examples/generic_lh2_full_scope_frequency_plan.json `
  --provider-worklist-only `
  --annual-conditions examples/equipment_annual_conditions.json `
  --scope-provenance "generic LH2 provider worklist" `
  --output results/20261009/provider_evidence/generic_lh2_worklist_campaign.json
```

이 컴파일 결과는 24개 event route와 24개 `uncomputed-provider-packet`
branch를 만들며, consequence request와 물리 case는 0개다. 따라서 실행 회계에는
모든 빈도 사건이 나타나지만 위험을 0으로 계산하거나 provider 방출을 대신하지 않는다.

`READY_FOR_PROVIDER_PACKETS`는 요청 형식과 사고 포트가 모두 준비됐다는 뜻이다. 결과가 계산됐다는 뜻은 아니다. 실제 provider packet이 들어오기 전에는 모든 사건이 `UNCOMPUTED`로 남는다.

`--model-binding`을 지정하면 각 작업 항목에 모델 상태와 사고 release export 상태가 함께 기록된다. 현재 일반 LH2 예제에서는 24개 항목 모두 정상 상태 모델은 `STATE_ONLY_BOUND`이지만 사고 release export가 `missing`이므로, 작업목록은 이 사유를 보존한 채 packet을 기다린다. 이 표시는 정상 유량을 사고 방출로 바꾸지 않기 위한 추적 정보다.

## 사건별 요청 규칙

| 빈도 release mode | 요청 packet | 허용 source operator | 종료 조건 |
| --- | --- | --- | --- |
| `hole` | `prism.resolved_release.v1` | `integrated_transient` 또는 액체 provider 경로 | provider가 선언한 실제 종료시간 |
| `instantaneous_inventory` | `prism.resolved_release.v1` | `equipment_inventory_depletion` 또는 `equipment_liquid_release` | `inventory_depletion` |
| `inventory_over_600s` | `prism.resolved_release.v1` | `equipment_inventory_over_600s` 또는 `equipment_liquid_over_600s` | 정확히 600초 |
| `two_sided_rupture` | `prism.resolved_release_set.v1` | `equipment_two_sided_rupture` | `two_sided_rupture` |
| `maximum_relief_discharge` | `prism.resolved_release.v1` | `equipment_emergency_relief` | `emergency_relief_discharge` |

구멍 사건은 provider의 `failure_opening_diameter_m`가 빈도 사건의 구경과 정확히 일치해야 한다. 600초 사건은 600초 이력과 질량·엔탈피 장부가 있어야 한다. 양단 파열은 두 개의 독립 출구를 가진 release set이어야 하며, 한쪽 출구를 복사해 양단으로 만들지 않는다. 릴리프 사건은 random leak 구경을 포함하지 않는 별도 `emergency_relief` packet이어야 한다.

정상 유량 JSON, 센서 압력·온도 시계열, 밸브 명령만 있는 자료는 이 작업목록을 통과하지 못한다. provider가 `component_id`, 사고 포트, 좌표, 방출 단계별 시간·질량·엔탈피, 종료 근거, source/result digest를 포함한 packet을 제출한 뒤에만 `campaign_template.py`의 exact-match compiler로 넘어간다.

## 현재 의미

이 작업목록으로 일반 설비의 24개 빈도 사건이 어떤 설비 방출 자료를 기다리는지 한 파일에서 추적할 수 있다. 따라서 “빈도는 있는데 방출이 없는 사건”을 시설 IR/F-N 합계에 몰래 포함할 수 없다. 실제 검사센터 자료는 별도 감사에서 사고 packet 0건으로 확인됐으므로 이 작업목록은 센터 사고빈도를 만들거나 센서 기반 빈도를 학습하지 않는다.
