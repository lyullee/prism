# PRISM 혼합 LH2 시설 캠페인 연결 기록

작성일: 2026-10-14  
대상: 일반적인 실외 액화수소 시설의 설비별 위험도 계산 연결  
실행 브랜치: `codex/prism-development`

## 이번 단계의 목적

기존에는 사고 방출 패킷을 한 종류씩 검사했다. 이번 단계에서는 하나의 일반 LH2 시설에서 발생할 수 있는 서로 다른 방출 family를 하나의 `RiskCampaign`으로 묶었다.

- 우발 누출: 탱크, 배관, 밸브, 펌프, 기화기, 재액화기
- 비상 릴리프 방출
- 재고 소진 방출과 600초 재고 방출
- 양단 파열 방출

각 사건은 자신의 설비 ID, 방출구 ID, 방출시간, 재고량, 방출 연산자를 유지한다. 사건의 빈도는 캠페인 실행 시 검토된 빈도표 이벤트에 한 번만 결합한다.

## 구현한 파일

- `scripts/build_lh2_mixed_provider_campaign.py`
  - 세 provider catalog를 읽는다.
  - 이벤트 ID별로 정확히 하나의 요청을 선택한다.
  - 같은 설비와 같은 구멍 크기를 공유하는 G4/G5처럼 물리 조건이 겹쳐도 이벤트 ID가 먼저 선택되므로 서로 잘못 결합되지 않는다.
  - `--rebase-positions`를 지정하면 provider의 일반 진단 좌표를 매니페스트의 같은 방출 포트 좌표로 명시적으로 배치한다.
  - 배관 길이 빈도를 한 점에 복사할 `location_weight`가 없으면 요청을 만들지 않고 `UNCOMPUTED`로 남긴다.

- `scripts/run_lh2_mixed_provider_campaign.py`
  - 컴파일된 캠페인을 고정된 SLABx-LH2, DynamicLH2PoolX, SLABx, TNO backend로 실행한다.
  - 실패, 연산자 제한, 영역 미완성, 명시적 미계산을 모두 결과에 기록한다.
  - p50/p95/p99는 한 번의 캠페인 안에서 실행된 사건 처리시간이며 1 Hz 서비스 보증이 아니다.

- `examples/generic_lh2_full_scope_annual_conditions.json`
  - 일반 실외 LH2 진단용 날씨와 `worker-01` 수용체를 선언한다.
  - 현장 인구자료가 아니며 예시 입력이다.

- `examples/generic_lh2_mixed_frequency_scenarios.json`
  - 문헌 빈도 중앙값, 사용 가능한 p05/p95, 독립 이벤트 비교를 선언한다.
  - 물리 재계산 없이 빈도만 바꾸며, 불완전한 시설 범위는 그대로 불완전하게 남긴다.

## 구조 연결 결과

입력 catalog는 다음과 같다.

- 우발 방출 21건
- 비상 릴리프 1건
- 양단 파열 set 2건
- 총 provider packet 24건

24개 이벤트가 모두 생성된 빈도 이벤트와 일치했다. 그중 19건은 요청 branch를 만들었고, 배관의 5개 hole event는 10 m 노출 빈도를 한 위치로 할당할 `location_weight`가 없어 5건을 명시적 `UNCOMPUTED`로 보류했다. 이는 배관 전체 빈도를 하나의 방출점에 몰아넣지 않기 위한 계약이다.

provider packet의 진단 좌표는 시설별 좌표와 다를 수 있다. 이번 실행에서는 `--rebase-positions`를 사용해 `port_id`가 같은 매니페스트 포트로 좌표를 옮겼다. 이 작업은 provider의 열역학·유량·재고 이력을 바꾸지 않고 시설 내 위치만 바꾼다. 실제 시설 적용에서는 이 매핑을 설비 모델 export 단계에서 확인해야 한다.

| backend 실패 | 9 |
| 위치·빈도 배분 미계산 | 5 |
| 알려진 기여 IR, worker-01 | `1.749e-05 / year` |
| 시설 전체 IR | 보류 |
| 시설 전체 F-N | 보류 |
| 총 fresh physics 사건 | 19 |

실제로 `EXECUTED`까지 도달한 사건은 비상 릴리프 1건, 기화기 G1/G2/G3 3건, 재액화기 G6 1건이다. 탱크 hole은 물리 계산은 시작됐지만 source operator가 일정 상태·개방 종료를 가정하므로 `EXECUTED_OPERATOR_LIMITED`로 남았다.

실패 원인은 다음과 같다.

1. 밸브 5건과 펌프 2건: 양의 rainout이 생겼지만 명시적인 pool footprint가 없어 backend가 중단했다.
2. 재액화기 G4/G5: 한쪽 방출구가 현재 바람에 대해 상류에 남아 있어 자동으로 하류 방향으로 회전시키지 않고 중단했다.
3. 배관 5건: 물리 계산 전 단계에서 길이 노출 빈도와 한 방출점의 위치 가중치가 없어 보류했다.

이 실패들은 0 위험으로 처리되지 않는다. 모두 시설 장부의 미계산 또는 실패 사건으로 남고 시설 총 IR/F-N을 차단한다.

## 빈도 불확실성 결과

결과 파일: `results/20261014/generic_lh2_mixed_facility_assessment.json`

시설 장부에는 다섯 시나리오를 넣었다.

- 중앙 문헌 빈도
- 설비별 p05와 중앙값 혼합
- 설비별 p95와 중앙값 혼합
- 사건별 독립 p05 비교
- 사건별 독립 p95 비교

계산된 사건만 다시 빈도 가중치를 적용했으며, 물리 결과는 재실행하지 않았다. `worker-01`의 알려진 기여 IR 범위는 다음과 같다.

- 중앙: `1.749e-05 / year`
- 낮은 문헌 빈도: `3.186433071805867e-07 / year`
- 높은 문헌 빈도: `1.0631967806999554e-03 / year`

이는 시설 전체의 신뢰구간이 아니다. 미계산 사건과 실제 현장 빈도 검증이 남아 있으므로 `facility_credible_interval=false`이다.

## 대표 배관 구간을 명시한 재실행

배관 사건을 계속 위치 미계산으로 둘 때와, 하나의 대표 1 m 구간을 명시할 때를 분리하기 위해 `examples/generic_lh2_mixed_frequency_plan.json`을 추가했다. 이 계획은 선언된 10 m 배관에 `location_weight=0.1`을 적용하고, 나머지 9 m는 별도 위치 검토가 필요하다고 기록한다. 10 m 전체 빈도를 하나의 포트에 복사한 것이 아니다.

대표 구간 계획의 결과 파일은 `results/20261014/generic_mixed_provider_campaign_weighted_result.json`이다.

| 항목 | 대표 1 m 구간 재실행 |
|---|---:|
| 이벤트 생성 | 24 |
| 요청 branch | 24 |
| 물리 실행 시도 | 24 |
| `EXECUTED` | 5 |
| `EXECUTED_OPERATOR_LIMITED` | 5 |
| backend 실패 | 14 |
| 위치 미계산 | 0 |
| 캠페인 처리시간 | 약 59.73 s |

배관 5건은 이제 빈도 위치 계약을 통과했지만, 모두 명시적인 pool footprint가 없어 backend에서 실패했다. 밸브 5건과 펌프 2건도 같은 pool 계약에서 실패했고, 재액화기 G4/G5는 양단 중 한쪽의 상류 handoff guard에서 중단됐다. 탱크 5건은 기존과 같이 연산자 제한 또는 domain incomplete로 남았다. 따라서 `results/20261014/generic_lh2_mixed_facility_assessment_weighted.json`도 시설 전체 IR/F-N을 보류한다.

이 재실행은 배관 빈도 배분 문제가 해결되면 바로 다음 물리 계약으로 진행할 수 있다는 것을 확인했다. 다음 구현은 provider가 계산한 pool footprint 또는 `no_rainout` 판정을 packet에 넣는 일이다.

## 선언된 pool footprint 진단

provider packet에 실제 시설 pool 형상이 아직 없으므로, 컴파일러에 `--pool-radius-m 0.005` 옵션을 추가했다. 이 옵션은 `footprint_origin=declared_sensitivity`인 작은 진단 footprint를 모든 요청에 넣을 뿐이며, 현장 바닥 형상이나 누출 면적을 추정하지 않는다.

결과 파일은 `results/20261014/generic_mixed_provider_campaign_pool_result.json`과 `results/20261014/generic_lh2_mixed_facility_assessment_pool.json`이다.

| 항목 | 대표 1 m + pool 진단 |
|---|---:|
| 물리 실행 시도 | 24 |
| `EXECUTED` | 5 |
| `EXECUTED_OPERATOR_LIMITED` | 12 |
| backend 실패 | 7 |
| 명시적 `UNCOMPUTED` | 0 |
| 캠페인 처리시간 | 약 154.40 s |

pool footprint를 넣자 배관·밸브·펌프의 “pool footprint 없음” 중단은 줄었다. 이후 bounded pool observation으로 전이밸브의 deadline 중단도 제거됐다. 현재 남은 실패는 세 transfer-line의 `x must be non-decreasing` puff handoff이고, 16건은 source operator가 일정 상태 또는 열린 종료를 선언해 operator-limited로 남았다. 따라서 미계산 branch는 없지만 실패·제한 사건이 남아 시설 전체 IR/F-N은 여전히 보류한다. 이 진단은 provider가 실제 pool 경계 또는 `no_rainout` 판정을 반환하는 다음 계약을 설계할 근거로 사용한다.

## 이번 보완 구현: 실제 풍하측 handoff와 소량 pool 관측

### 양단 방출의 풍향 조건 handoff

재액화기 G4/G5의 반대 방향 방출은 SLABx-LH2가 처음 선택한 상태가 가스 상태·풍향 정렬 조건을 만족해도 방출점의 풍상측에 남을 수 있었다. 이제 PRISM은 그 상태를 바로 SLABx에 넘기지 않는다. 같은 SLABx-LH2 전이 표에서 다음 조건을 모두 만족하는 실제 행을 찾는다.

- 액체 성분이 허용 오차 이하
- 바람 정렬 오차가 10° 이하
- ENU 위치를 풍하측 단위벡터에 투영한 값이 0보다 큼

조건을 만족하는 다음 행이 없으면 `vector transition remains upwind within the declared horizon`으로 사건을 보류한다. 방출 방향을 임의로 회전하거나 방출원을 이동하지 않는다. 보완 후 G4/G5는 기존 `FAILED`에서 `EXECUTED_OPERATOR_LIMITED`까지 도달한 표적 진단이 확인됐다. 이는 양쪽 plume의 상호작용을 계산했다는 뜻은 아니며, 두 endpoint를 각각 계산할 수 있는 기반을 만든 것이다.

### 작은 rainout의 시간 관측 세분화

아주 작은 방출에서는 DynamicLH2PoolX가 첫 번째 젖은 격자를 보고하기 전에 유효한 증발 질량을 장부에 기록할 수 있다. PRISM은 이 구간을 무한히 잘게 쪼개지 않는다. 먼저 provider가 준 평가 시계를 사용하고, 양 끝 면적이 모두 0인 구간이 실제로 남을 때만 한 번 더 세분화한다. 이후에도 젖은 격자가 없으면 요청에 명시된 `radius_m`의 원형 source footprint를 사용해 질량을 보존하고, 다음 정보를 결과에 기록한다.

- `raw_packet_count`, `coarsened_packet_count`: 풀 장부와 SLABx에 넘긴 관측 구간 수
- `coarsening_target_packet_count=8`: 인접 구간을 최대 8개 관측 궤적으로 묶는 실행 예산
- `zero_area_packet_fallback_count`: 젖은 격자보다 먼저 발생한 증발 구간 수
- `zero_area_packet_fallback_method`: 최초 downstream wet area 또는 명시된 source area 사용

이 병합은 DynamicLH2PoolX의 질량 장부를 바꾸지 않고, 후속 SLABx 호출 수만 제한한다. 전이밸브 `AREA_0.01%` 표적은 약 9초에 최종 피해 단계까지 도달했고 방출 `3.164317187981656e-05 kg`, pool 증발 `3.164317187835929e-05 kg`, 종단 잔차 `-2.74377481823366e-20 kg`를 기록했다. 이는 명시된 진단 footprint의 계산 확인이지, 실제 시설 바닥 형상의 검증값은 아니다.

### 아직 보류하는 full-bore 사건

full-bore `transfer-line/AREA_100%`는 SLABx의 유한 방출 puff 전환 첫 점이 이전 점보다 뒤로 이동해 `x must be non-decreasing` 계약을 위반한다. PRISM은 이 값을 정렬하거나 방출원을 임의로 이동하지 않고, `finite-release puff handoff remained non-monotonic`으로 보류하도록 진단 메시지를 구체화했다. 따라서 full-bore 물리 연결은 아직 완료되지 않았다.

## 보완 코드의 24건 전체 재실행

보완 코드를 반영한 공식 재실행 결과는 `results/20261014/generic_mixed_provider_campaign_refined_pool_result.json`에 저장했다.

| 항목 | 보완 코드 전체 재실행 |
|---|---:|
| 물리 실행 시도 | 24 |
| `EXECUTED` | 5 |
| `EXECUTED_OPERATOR_LIMITED` | 16 |
| backend 실패 | 3 |
| 명시적 `UNCOMPUTED` | 0 |
| 캠페인 처리시간 | 약 215.90 s |
| case p95 / p99 | 약 20.46 s / 58.24 s |

실패 3건은 transfer-line `AREA_0.1%`, `AREA_1%`, `AREA_100%`의 유한 방출 puff handoff 비단조다. SLABx 궤적을 정렬하거나 방출 방향을 바꾸지 않고 fail-closed로 보류했다. 전이밸브의 180초 deadline 실패는 제거되어 `EXECUTED_OPERATOR_LIMITED`로 기록된다. 시설 IR/F-N은 여전히 실패·operator-limited 사건과 실제 pool 형상 미확정 때문에 보류한다.
