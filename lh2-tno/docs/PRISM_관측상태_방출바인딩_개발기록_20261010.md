# PRISM 관측 상태와 방출 packet 바인딩 감사

## 왜 이 감사가 필요한가

액화수소검사지원센터 자료에는 실제 운전 상태가 있습니다. 인수 탱크, 저장 벤트,
공급·기화 경계의 압력·온도·차압을 합치면 8,955개 시계열 표본입니다. 이 자료는
디지털 트윈의 현재 상태를 확인하고 모델을 보정하는 데 유용합니다.

그러나 압력이 올랐다는 사실만으로 사고 방출이 발생했다고 말할 수는 없습니다. 어떤
개구에서 얼마만큼 새었는지, 방출이 언제 끝났는지, 어떤 provider 계산이 그 결과를
만들었는지, 그 packet이 독립 검토를 통과했는지가 별도로 필요합니다. 관측 자료를
사고 원장이나 빈도로 자동 변환하면 실제 시설 위험도를 과장할 수 있습니다.

그래서 PRISM은 다음 세 연결을 모두 명시적으로 요구합니다.

1. 관측 source가 어느 관측 component에 속하는가.
2. 그 관측 component가 일반 PRISM 시설의 어느 `facility_component_id`와 같은가.
3. 검토된 provider 방출 packet의 `event_id`가 그 시설 component를 실제로 가리키는가.

현재 센터 자료의 관측 component ID는 `lh2-intake-tank`, `lh2-storage-vent`,
`lh2-supply-vaporizer-boundary`입니다. 일반 시설 원장의
`storage-tank-01`, `pressure-relief-vent-01`, `ambient-vaporizer-01`과의 대응은
설비 도면·태그·운영자 확인 없이 추정하지 않습니다. 따라서 현재 바인딩 manifest는
비어 있고 감사 결과는 `NO_STATE_TO_RELEASE_BINDING`입니다. 이는 상태 자료가 없다는
뜻이 아니라, 사고 방출 packet으로 승격할 수 있는 검토된 연결이 아직 없다는 뜻입니다.

## 감사 실행

```powershell
python scripts/audit_observed_state_release_binding.py `
  --observed-state-evidence examples/inspection_center_observed_state_evidence.json `
  --provider-packet-input-audit results/20261026/native_full_scope_union_assessment/provider_packet_input_audit.json `
  --binding-manifest examples/inspection_center_observed_state_release_binding_manifest.json `
  --output observed_state_release_binding_audit.json
```

출력 스키마는 `prism.observed_state_release_binding_audit.v1`입니다. 출력에는 관측
component 수, 연결된 component 수, 연결되지 않은 component 수, 확인된 provider
event 수와 각 행의 차단 사유가 들어갑니다. 결과는 진단용이며 사고빈도·방출량·누출
지속시간·IR/F-N을 계산하거나 만들지 않습니다.

## 검토된 연결을 추가하는 방법

운영자와 설비 문서로 대응을 확인한 뒤에만 다음처럼 manifest에 행을 추가합니다.

```json
{
  "schema_version": "prism.observed_state_release_binding_manifest.v1",
  "bindings": [
    {
      "binding_id": "intake-tank-to-storage-tank-01",
      "observed_component_id": "lh2-intake-tank",
      "facility_component_id": "storage-tank-01",
      "source_ids": ["inspection-center-intake-pressure"],
      "provider_event_ids": ["storage-tank-01-small-leak-001"],
      "review_status": "reviewed"
    }
  ]
}
```

`source_ids`는 관측 원장에 실제로 존재해야 하고, `provider_event_ids`는 현재
provider packet 입력 감사에서 자격을 통과한 event여야 합니다. component가 다르거나
검토 상태가 없으면 해당 행은 `STATE_MAPPING_UNQUALIFIED`로 남습니다. 모든 관측
component가 검토된 provider event에 연결될 때에만 `STATE_AND_PROVIDER_RELEASE_BOUND_DIAGNOSTIC`가
됩니다. 이 상태도 독립 물리검증, 주요사고 전체범위, 시설 IR/F-N 게이트를 자동으로
열지 않습니다.

## 상태 일관성 장부와의 연결

현재 union의 상태 일관성 감사는 이 파일을 선택적으로 읽습니다.
`CURRENT_STATUS.json`과 `DEVELOPMENT_GOAL.json`은 같은 결과 파일과 결과 상태를
가리켜야 하며, 하나라도 다른 파일을 가리키면 감사가 `INCONSISTENT`가 됩니다.
현재 결과는 관측 component 3개, 연결 0개, 미연결 3개입니다.
